## 1. 本次改动内容（相对 09-14 交接）

### 1.1 推送改为"按需连接"模式（核心改动）

**背景**：常连模式（`PUSH_ALWAYS_ON=1`）下，腰端 WiFi 长期连着热点，射频必须跟随热点信道。
安卓热点会自动选"最空"的 2.4G 信道（1/6/11 三选一），手机不可控地漂移（实测 ch6→ch11）。
每次漂移 = 腰端射频跟着跑 ≠ 腕端 ESP-NOW 固定 ch6 → **腕端数据链路静默断流**（rx 不涨、LED 慢闪）。

**方案**（`config.h` → `PUSH_ALWAYS_ON=0`）：

| 阶段 | 行为 |
|---|---|
| 平时 | 不连 WiFi，腰端常驻 `ESPNOW_CHANNEL=6` 只收腕端包 |
| 报警确认后 | 连热点（超时 10s）→ WxPusher 推送 → 失败重试 6 次×15s |
| 推完/放弃 | `WiFi.disconnect()` + `esp_wifi_set_channel(6)` 跳回，腕端链路无感恢复 |

- **收益**：对任意信道的热点都鲁棒，不再要求信道对齐
- **代价**：微信收到时间 ≈ 7s 取消窗 + ~5s 连接 + ~4s 发送 ≈ **13~18s**（演示时提前打好招呼）
- 推送过程不影响蜂鸣器（已转入"长鸣"阶段持续响）

### 1.2 取消窗 10s → 7s

`ALARM_CANCEL_WINDOW_MS = 7000`。演示节奏更快。
**答辩被问"7 秒够吗"时**：量产定位建议 ≥8s（给老人留反应时间），下限 6s，7s 是演示权衡值（config.h 有注释）。

### 1.3 硬件集成批次（v0.5，commit `36c53e8`，已推送）

- 腕端状态 LED（`hw_led.h/.cpp`，GPIO8）：2s 心跳短闪=正常；1s 慢闪=链路故障（连续 10 次发送失败）；200ms 快闪=MPU 离线
- 腰端有源蜂鸣器两段式：取消窗内急促哔哔（300ms 响/500ms 周期）→ 推送后长鸣（800ms 响/1000ms 周期）
- EC11 编码器替代取消按钮：按压脚接 GPIO5（等效按钮，INPUT_PULLUP），旋转脚悬空
- 实测状态：板间通信 rx 正常涨、lost=0、lastAge 个位数 ms

## 2. 系统现状一句话（答辩自我介绍用）

**腕端 XIAO ESP32S3 自制 PCB（MPU6050 50Hz）→ ESP-NOW 无线 → 腰端 ESP32-S3 大板三阶段触发 + 15 棵随机森林判决 → 两段式蜂鸣本地报警 → 7 秒可取消 → 微信远程推送（WxPusher）。**

### 2.1 核心指标（数据来源：SisFall 公开数据集，留出集按人划分，部署门限 0.40）

| 指标 | 数值 |
|---|---|
| 灵敏度（跌倒检出率） | **96.0%** |
| 特异度（日常活动不误报） | **98.4%** |
| 老年日常误报率 | 4.6% |
| CNN 二级仲裁（影子模式） | 真实灵敏度 70~78%，暂无判决权 |
| 板间链路 | 50Hz，正常时 lost=0 |

### 2.2 工程亮点（可当"创新点"讲）

1. **双传感源融合架构**：腕+腰两个位置独立采集，比单点方案信息量大（腕端否决票 v1 已预留：`ENABLE_WRIST_FUSION`，标定后开启）
2. **RF 主判决 + CNN 二级仲裁的保守架构**：CNN 不抢班夺权（RESCUE/VETO 影子模式跑对照数据），体现"可解释、可回退"的工程决策
3. **按需推送的射频共存设计**：单射频芯片上解决"ESP-NOW 固定信道 vs WiFi 热点信道漂移"的矛盾（§1.1，这是一个真实的工程问题）
4. **两段式报警 + 可取消**：先急促提醒本人（误报可按掉），7s 后才长鸣+推送叫家人——尊重老人尊严，避免"狼来了"
5. **训练域=部署域**：SisFall 200Hz→50Hz 降采样训练，与上板采样率一致；C++/Python 双语言回放 0 不一致

## 3. 演示流程脚本（答辩现场用）

**演示前 10 分钟准备**（缺一不可）：
- [ ] 腰端供电：≥6.65V（9V 适配器/PD 诱骗线；**5V 充电宝直连 Type-C 开不了机**）
- [ ] 手机热点开启，**停留在热点设置页面**（vivo"无设备连接自动关热点"高发；设置里关掉该选项更稳）
- [ ] 收推送的手机微信已关注 WxPusher 应用（历史收到过 code=1000 那台）
- [ ] 腕端开机后 LED 2s 心跳闪（若 1s 慢闪=链路故障，先重启腰端）

| 步骤 | 操作 | 观众看到 | 背后发生 |
|---|---|---|---|
| 1 | 双板上电，腰端静置 5s | 腕端 LED 心跳 | baseline 基线采集（`baseline tilt=xx, detector armed`） |
| 2 | 正常走两步、坐下起立 | 什么也不响 | 展示特异度（日常不误报） |
| 3 | **长按腕端按钮 1s**（模拟跌倒） | 蜂鸣器急促哔哔 | 三阶段触发→RF 判决→报警状态机 |
| 4 | **按一下编码器** | 蜂鸣停止 | 误报可取消（7s 取消窗） |
| 5 | 再次长按，这次**不取消** | 哔哔 7s → 转长鸣 | 推送任务连热点发 WxPusher |
| 6 | 举手机 | **微信收到"跌倒报警"** | ~13~18s 到达，提前说明 |
| 7 | （可选）贴串口日志 | rx 涨 lost=0 | 证明链路健康 |

**兜底**：提前录一遍完整流程的视频，现场设备出意外就放视频。

## 5. 答辩 Q&A 备查

- **为什么用随机森林不用神经网络？** RF 在我们的数据上灵敏度 96% 显著优于 CNN v2 的 70~78%，且可解释、C++ 部署简单、推理开销可忽略。CNN 保留为二级仲裁（影子模式），攒数据后再授权——这是数据驱动的选择，不是能力问题。
- **数据集哪来的？** SisFall 公开数据集（含真跌倒+老年日常），按人划分防泄漏；200→50Hz 降采样保证训练域=部署域。
- **误报怎么办？** 三道防线：①特异度 98.4% ②7s 取消窗 ③腕端否决票（预留）。
- **老人没带手机 / 没网怎么办？** 本地蜂鸣器独立于网络；推送只是增项。
- **隐私？** 全部计算在设备端（边缘计算），不上云、不传原始数据，只发一条报警文本。
- **为什么双板？** 腰部姿态信息量大（跌倒=冲击+姿态剧变），腕部补充手臂动作；单点方案二者只能得其一。
- **信道漂移怎么解决的？** 见 §1.1，按需连接模式（这是我们自己踩坑踩出来的方案）。

## 6. 已知坑速查（现场应急）

| 症状 | 原因 | 处置 |
|---|---|---|
| 推送时 `WiFi connect timeout` | 热点被手机自动关了 / 手机连着别的 WiFi | 停留在热点设置页；关 WiFi 只留热点 |
| 腕端 LED 1s 慢闪 | 链路故障 | 重启腰端（信道被占/漂移残留） |
| 腰端 Type-C 供电不启动 | 电压 <6.65V | 换 ≥6.65V 供电 |
| 腕端插电池不亮 | （已修）BAT 飞线已补焊，SW2 已 P4 锡桥旁路 | 插电池=开机，无需开关 |
| OLED 不亮 | 模块烧毁待换 | 不影响主链路，忽略 |
| 烧录不上（腰端） | 用错 Type-C 当烧录口 | 烧录用 **Micro USB**（CH340） |
