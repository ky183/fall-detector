## 1. 本次改动内容（相对 v0.5）

### 1.1 推送文案规范化（腰端 `config.h` 三个宏）

| 项 | 新文案 |
|---|---|
| 消息标题 | `【跌倒报警】请及时关注` |
| 正文 | `【跌倒报警】设备检测到疑似跌倒，7 秒内未按取消键，已确认报警。请尽快联系老人确认状况。` |

只改宏字符串，`net_pusher.cpp` 的拼包逻辑零改动。

### 1.2 报警状态回显：腰→腕 `PKT_ACK`（新通信方向）

协议里预留的 `PKT_ACK`（type=0x03）正式启用，载荷 `AckPayload{alarmState, remainSec}`（2 字节，包大小不变仍 38B）：

- **腰端**（`net_espnow.cpp` 新增 `espnow_send_ack()`）：报警状态变化立即发；取消窗内 2Hz 重发；推送后 1Hz 重发。目标 MAC 取自首个收到的腕端数据包（自动缓存 + add peer，无需配置）。开关 `ENABLE_ALARM_ECHO`（置 0 = 射频行为回到 v0.5）。
- **腕端**（`net_espnow.cpp` 新增接收回调，原本只发不收）：只处理 `PKT_ACK`，只写 4 个 volatile 变量，不碰采样/发送。

### 1.3 腕端 OLED 四级页面（产品化 UI）

优先级从高到低（`ui_oled.cpp`）：

| 页面 | 触发 | 内容 |
|---|---|---|
| 报警弹窗 | alarmState=WAIT | `! FALL DETECTED !` 反色条 + 剩余秒**大字倒计时 7→1** + `WAIST KNOB=CANCEL` |
| 已推送页 | alarmState=SENT | `! FAMILY ALERTED !` + `NOTIFYING VIA WECHAT` |
| 已取消页 | 收到 NORMAL（3 秒） | `CANCELLED` + `FALSE ALARM` |
| 正常页 | 默认 | 运行时长大字 + `STEPS n` + `LINK: OK` |

- **正常页布局开关 `DEBUG_DISPLAY`**（腕端 `config.h`）：0=产品布局（上述）；1=原调试布局（SVM 大字+事件计数）。调试能力保留，一改宏即回。
- 显示滞后 ≤0.5s（OLED 500ms 刷新周期）；推送连 WiFi 期间腕端弹窗可能短暂停在旧状态（信道被占用，推完自动恢复）——均为设计内行为。
- 演示脚本 P17 口径：长按 **1 秒**（`BTN_LONG_PRESS_MS=1000`，中途试过 2s 又按演示需求改回）。

### 1.4 步数统计（腕端纯本地，新模块 `pedometer.h/.cpp`）

- **架构决策：腕端本地算**——本机 50Hz SVM 直接喂入，本地计数、本地 OLED 显示。零通信改动、零协议改动、腰端零依赖。答辩口径：腕端从"只采集转发"升级为"数据本地产出健康指标"。
- 算法（规则法，不训练模型）：动态幅值 `|SVM−9.81|` → EMA 低通（α=0.2）→ 阈值 2.0 m/s² 过阈记候选峰 → 迟滞回差（阈值一半）防抖 → 两峰间隔窗 250~2000ms。
- **两级防误报**：① 阈值挡日常小幅动作；② **连续 4 步确认**——孤立晃动（1~3 峰）不计数，连续走出第 4 步时把前几步一起补记；停走 >2s 重新确认。与报警取消窗同一设计哲学："宁可多一道确认，不做不可靠判定"。
- 存储为 RAM（重启清零）——调试期决策；日后要持久化加 NVS 低频落盘（每小时+每千步）即可，接口已预留 `pedometer_reset()`。
- 调参法（写进 config 注释）：`DEBUG_DISPLAY=1` 走路看 SVM 峰值，阈值 ≈ 峰值动态幅值 × 0.7。**最终调参请按终审实际佩戴方式标定**（手持与绑腕数值差异大）。开关 `ENABLE_PEDOMETER`。

### 1.5 WiFi 推送加固（★重要 bug 修复，与时间功能无关）

**修复：推送重试卡死**。原 `connect_wait` 连接超时后不做清理，STA 芯片仍在后台重试连接，15 秒后的下一次 `WiFi.begin()` 被拒（串口铁证：`wifi:sta is connecting, cannot set config`），6 次重试全部假失败。修复：`WiFi.begin` 前先 `WiFi.disconnect()` 清残留 + 超时路径终止后台连接。**此缺陷 v0.2 起就存在，只是"热点先开"的演示流程从未触发过**——任何"第一次连接失败再重试"场景（热点晚开、信号弱）都会踩中，v0.5 同样受影响，属净收益修复。

**新增：失败自动扫描诊断**。推送连接超时后自动全信道扫描 2~4 秒，打印：扫到的 AP 总数、目标热点（信道/信号/加密方式）或"目标不在广播"。本次排查中它一锤定音地区分了"固件问题"与"热点侧问题"（见 §3.1）。

### 1.6 已移除：NTP 时间同步（做过、验证过、主动撤掉）

曾实现"腰端开机一次性 NTP → epoch 经 PKT_ACK 下发 → 腕端走时显示真实时钟"全链路（含失败重试、报警避让），联调中被手机热点问题干扰（见 §3.1），按"推送可靠性优先"原则主动移除。**实现完整封存于 git 历史 `d337728`~`1c87b4f`，恢复直接 cherry-pick**。若日后重启此功能，推荐改用"腰端推送成功时顺手 NTP（复用已建立的 WiFi 连接，零新增射频窗口）+ 时间存 NVS 断电保持"，或腕端低频自连（腕端连 WiFi 期间腰端算法自动回退本地 MPU 判定，安全性已有兜底）。

## 3. 调试/演示注意事项（本周实测踩坑，全部有据）

### 3.1 手机热点"假死"（新踩坑，终审必查）

现象：热点开关显示"开着"，但 ESP32 扫描全信道找不到它（`diag: TARGET AP NOT in air`），任何设备都连不上；**重启热点立即恢复**。伴随已知问题：安卓"无设备连接自动关热点"（vivo 高发，演示 Checklist 已有预警）。

**终审演示前固定动作**：① 关闭"无设备连接自动关闭热点"选项；② **上电前重启一次手机热点**（重启即排假死，比"检查开着"可靠）；③ 停留在热点设置页面。

### 3.2 腰端供电与蜂鸣器（待最终确认）

蜂鸣器报警变为"很小的哒哒声"——最大嫌疑是**用 Micro USB（烧录口）长期供电**（5V 且电流弱，蜂鸣器拉电流时电压跌落）。诊断树：换 Type-C/DC ≥6.65V 供电触发报警 → 仍小则蜂鸣器直连 3.3V/5V 测本体 → 本体坏换备件（有第二个）。**演示 Checklist 的"≥6.65V 供电"一条在终审是硬性的。**

### 3.3 lost 计数口径

`lost` 是累计值不回零。WiFi 连接/扫描期间（报警推送、诊断扫描）腕端数据必然断流几十到几百包——属设计内。**看增量不看绝对值**：射频空闲期 lost 增量应为 0。

### 3.4 演示新可展示点

- 报警时腕端 OLED 弹窗+大字倒计时（"三个瞬间"旁白里的"什么时候响"现在有画面）
- 取消后腕端 `CANCELLED` 页
- 正常页 `STEPS`：现场走几步数字跳（连续 4 步起跳，晃一下不涨——可当小互动）
